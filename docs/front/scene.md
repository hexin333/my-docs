# 场景相关

## 浏览器渲染过程

浏览器渲染是一个从字节到像素的流水线过程，核心分为「资源加载」和「渲染管线」两大阶段

::: details 详情

```
输入 URL
    │
    ▼
DNS 解析 → TCP 连接 → 发送 HTTP 请求 → 接收响应
    │
    ▼
下载 HTML → 解析 HTML 构建 DOM 树
    │           │
    │           ▼
    │      遇到 <link> CSS → 下载并解析 CSS → 构建 CSSOM 树
    │           │
    │           ▼
    │      遇到 <script> JS → 下载并执行 JS（阻塞解析）
    │           │
    ▼           ▼
    └──── DOM + CSSOM ──→ 合并生成 Render Tree（渲染树）
                              │
                              ▼
                         Layout（布局/重排）
                              │
                              ▼
                         Layer（分层）
                              │
                              ▼
                         Paint（绘制/重绘）
                              │
                              ▼
                         Composite（合成）→ 显示到屏幕
```

:::

## 浏览器的缓存

浏览器缓存的本质是用空间换时间——将已下载的资源（JS、CSS、图片等）保存在本地（内存或磁盘），下次访问时优先复用，减少网络往返、降低服务器压力、加速页面渲染。

::: details 详情

- 强缓存 vs 协商缓存
  | 维度 | 强缓存 | 协商缓存 |
  | ------------ | --------------- | --------------- |
  | **核心逻辑** | 浏览器自己算时间，没过期就直接用 | 过期后问服务器，资源没变就继续用 |
  | **是否发请求到服务器** | **不发请求** | **发请求**（仅做验证，不下载文件） |
  | **命中后状态码** | `200 (from memory cache)` 或 `200 (from disk cache)` | `304 Not Modified` |
  | **命中后响应体** | 无（读本地） | **无**（读本地） |
  | **未命中时状态码** | 走协商缓存或直接 `200`（重新下载） | `200`（返回新资源 + 新缓存头） |
  | **控制头 / 响应头（服务端设置）** | `Cache-Control: max-age=3600`指定资源在缓存中的最大存储时间（秒）<br>`Expires: Wed, 21 Oct 2026 07:28:00 GMT`（HTTP/1.0遗留）<br>`Cache-Control: immutable`声明资源在有效期内不会改变 | `Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT`<br>`ETag: "33a64df5"` |
  | **请求头（浏览器自动携带）** | 无 | `If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT`<br>`If-None-Match: "33a64df5"` |
  | **验证方式** | 当前时间与浏览器拿到资源时间对比，大于max-age就走协商缓存 | 服务器对比 `ETag` 指纹或 `Last-Modified` 时间（一般是验证ETag资源标识，精确验证） |
  | **优先级** | 先检查 | 强缓存失效后才进入协商缓存 |
  | **性能** | 最优（0ms 网络耗时） | 次优（有 1 次 RTT 往返，但不下载 body） |
  | **适用资源** | 不常变的静态资源（JS、CSS、图片） | 可能更新但希望节省带宽的资源（HTML、API） |

:::

## script 标签的 defer 和 async 有什么区别

async 是「下载完就执行」（插队执行，顺序乱）

defer 是「下载完等着，HTML 解析完再按顺序执行」（排队到最后，顺序稳）

::: details 详情
| 维度 | 无属性（默认） | `async` | `defer` |
| -------------- | --------------- | --------------- | ----------------- |
| **下载时机** | 阻塞 HTML 解析，立即下载 | **不阻塞** HTML 解析，后台并行下载 | **不阻塞** HTML 解析，后台并行下载 |
| **执行时机** | 下载完**立刻执行**，执行期间阻塞解析 | 下载完**立刻执行**，执行期间阻塞解析 | 等 HTML **完全解析完成后**才执行（在 `DOMContentLoaded` 之前） |
| **执行顺序** | 按出现顺序执行 | **不保证顺序**，谁先下载完谁先执行 | **严格按出现顺序**执行 |
| **是否等 DOM 就绪** | 不等 | 不等 | 等（执行时 DOM 已构建完成） |
| **适用场景** | 必须立即执行的脚本（极少用） | 独立脚本，不依赖 DOM 和其他脚本（如统计代码、广告 SDK） | 需要操作 DOM 或依赖其他脚本的业务代码（如 React/Vue 入口文件） |

:::

## 单页应用和多页应用的对比

单页面应用（SPA）比多页面应用（MPA）在页面切换和后续交互时更快，核心原因在于避免了整页重建，而非绝对意义上的"什么都快"。

::: details 详情
| 维度 | 单页面（SPA） | 多页面（MPA） |
| ---------- | ------------- | ------------- |
| **页面切换机制** | 客户端路由拦截，**局部更新 DOM** | 浏览器**完整跳转**，重新请求 HTML |
| **资源加载** | 首次加载后，JS/CSS 已缓存；后续只拉取**少量 JSON 数据** | 每次切换都重新下载 HTML，并重新解析执行 CSS/JS |
| **渲染范围** | 只替换变化的部分（如 `<router-view>` 内容） | 从白屏开始，**重新构建整棵 DOM 树 + CSSOM + Layout + Paint** |
| **状态保持** | 页面状态、滚动位置、表单数据**不丢失** | 页面刷新，内存状态全部清空，需重新初始化 |
| **视觉体验** | 无白屏闪烁，可做过渡动画 | 明显的**整页刷新闪烁** |

:::

## 页面加载缓慢的常见原因

页面加载慢通常从网络传输、资源体积、渲染阻塞、服务端响应四个维度排查。

::: details 详情
| 维度 | 具体原因 | 典型表现 |
| --------- | --------------------- | -------------- |
| **网络** | 带宽低、延迟高、DNS 解析慢、CDN 节点远 | 所有资源加载都慢，TTFB 高 |
| **服务端** | 接口响应慢、数据库慢查询、服务端渲染耗时长 | TTFB（Waiting）时间 > 1s |
| **资源体积** | 图片未压缩/未转 WebP、JS/CSS 未压缩、未开 Gzip/Brotli | 单个 JS 几 MB，图片几十 MB |
| **请求数量** | 小文件过多、未合并、未用 HTTP/2 多路复用 | Network 面板瀑布流很长 |
| **阻塞渲染** | CSS/JS 放头部且未加 `defer/async`、同步脚本阻塞解析 | 白屏时间长，First Paint 晚 |
| **第三方脚本** | 统计、广告、客服 SDK 加载失败或超时 | 页面等第三方资源，瀑布流尾部有长条 |

:::
